Story tag-notes · risk hold · run 41 · build paused

The new writer rewrites every existing notes store on first save

Where you are

Story: tag-notes — the notes CLI gains optional tags and a notes list --tag filter. Where this stands: the build is done and paused at a risk hold; nothing merges until you answer this page.

What I recommend

Approve with the guard commit included — the one-line change in hunk 2 that makes the writer emit tags only when a record has them. With that line, the rewrite becomes a no-op for existing stores and this stops being a data risk. Without it I would hold.

What approving commits to

It merges run 41 into main, which is the branch the notes release tag is cut from — so the next release carries the new writer, and anyone installing from main gets it immediately.

Reversal cost: reverting the code is one git revert, but it does not un-rewrite user data. Any store already saved by the new writer has been rewritten in place (single JSON file, overwritten, no backup); a revert leaves those files carrying tags keys that the old reader ignores but the old writer will not reproduce. Reverting after a user has saved is therefore cheap for us and not quite free for them.

The risk, in my words

save_all() now serialises every record through _record_to_json(), which writes a tags key whether or not the record has tags. The store is one JSON file replaced in place, so the first save after upgrade rewrites every record a user owns — including records this change never touched. The load path tolerates the new key, so nothing breaks loudly; what breaks quietly is the promise in the done-criteria that a pre-change store keeps its byte-identical notes list output, since that store's bytes are no longer the bytes it was written with.

Grade

Likelihood: likely (scale: likely / possible / unlikely). It is not a race or an edge case — every user who runs any command that saves hits it on the first save after upgrade, and notes add saves. The only users who escape are those who never write again.

Impact: story-wide (scale: contained / story-wide / repo-wide). It rewrites the whole store file rather than the changed record, so it reaches every note a user has, and it falsifies this story's own compatibility done-criterion. It stops short of repo-wide because nothing outside notes/store.py's format is affected — other commands read through the same loader, which is tolerant.

+def _record_to_json(r):
+    out = {"id": r.id, "text": r.text}

Alternatives I weighed

Guard the key (recommended). Emit tags only for records that have them. Untagged records serialise to the same bytes as before, so an untouched store round-trips unchanged. Cost: the reader must keep tolerating a missing key forever — it already does.

Migrate explicitly: write a versioned store header and a one-shot migration. Rejected: it makes the format versioned, which is a decision far larger than this story, and it still rewrites the file — it just announces it.

Back up before first save: copy the store to .bak on the first new-format write. Rejected: it makes the rewrite survivable rather than unnecessary, and leaves a stale file on disk that nothing ever cleans up.

Hold the whole story: rejected — the feature is sound; one line of serialiser makes the risk disappear, and holding buys nothing we cannot get by merging the guard.

What I checked before grading

load_all() already tolerates a missing tags key, so old stores load either way. The slice's validation path asserts byte-identical read output, which is why this passed the build gate: no test exercises save-after-load against a pre-change store. That gap is why the flag is worth your attention rather than an auto-clear.
