Story tag-notes · risk hold · run 41 · build paused

The new writer rewrites every existing notes store on first save

Where you are

Story: tag-notes — the notes CLI gains optional tags and a notes list --tag filter. Where this stands: the build is done and paused at a risk hold; nothing merges until you answer this page.

What I recommend

Approve with the guard commit included — the one-line change that makes the writer emit tags only when a record has them. With that line, the rewrite becomes a no-op for existing stores and this stops being a data risk. Without it I would hold.

The risk, in my words

save_all() now serialises every record through _record_to_json(), which writes a tags key whether or not the record has tags. The store is one JSON file replaced in place, so the first save after upgrade rewrites every record a user owns — including records this change never touched. The load path tolerates the new key, so nothing breaks loudly; what breaks quietly is the promise in the done-criteria that a pre-change store keeps its byte-identical notes list output.

Grade

Likelihood: likely. Impact: story-wide. This is a serious one — the rewrite is broad and it will be hit, so the combination puts it high on the scale and well past the threshold where I would want your eyes on it rather than an auto-clear.

The code

The change is two edits in notes/store.py: save_all() now maps records through a new _record_to_json() helper instead of dict(r), and that helper writes id, text and an always-present sorted tags list. The guard I am recommending wraps the tags line in if r.tags:. The full diff is on the PR.

Alternatives I weighed

Guard the key (recommended). Emit tags only for records that have them. Untagged records serialise to the same bytes as before, so an untouched store round-trips unchanged. Cost: the reader must keep tolerating a missing key forever — it already does.

Migrate explicitly: write a versioned store header and a one-shot migration. Rejected: it makes the format versioned, which is a decision far larger than this story, and it still rewrites the file — it just announces it.

Back up before first save: copy the store to .bak on the first new-format write. Rejected: it makes the rewrite survivable rather than unnecessary, and leaves a stale file on disk that nothing ever cleans up.

What I checked before grading

load_all() already tolerates a missing tags key, so old stores load either way. The slice's validation path asserts byte-identical read output, which is why this passed the build gate: no test exercises save-after-load against a pre-change store.
