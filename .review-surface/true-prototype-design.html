The claim to prove

Today the prototype proves “this specific 7-stage pipeline works.” The system claim is “agnostic skill/agent/workflow nodes, connected via the board” — and the falsifiable test is: define a second, different workflow in config only, and the same engine runs it with zero code changes.

The blackboard design is already decided through five HITL rounds — event (namespace · topic · key · kind · provenance), eight communication kinds, action = trigger → body → emitter, observed vs claimed reads with board-owned cursors, leases, in-tray, firing log, failure = signal → triage action. The Rust crate is a 184-line stub (Event + JSONL store), so the decisions are finished; the code isn't. The prototype should consume the decided semantics, not reinvent them — and this also delivers blackboard acceptance scenario #1 (“Cadre stage→stage”, NEX-217).

The four pieces

1 · Board (semblance)

One SQLite file in the data dir implementing the decided semantics faithfully: typed events with the fixed header (namespace, topic, key, kind, provenance-from-env), the eight kinds validated at write, observed reads with board-owned cursors, claimed reads with lease + deadline, in-tray as consumed-once read on own key, separate firing log, correlation_id / visible_after headers. Nothing invented — schema transcribed from the decision entries.

2 · Node registry

The registry from the approved plan, holding node definitions: name, versioned prompt, model pin, what it reads (trigger shape), what it emits (kinds). Content-addressed versions + lineage; git-backed export dir. Stage sessions get their prompt by version id, and every run records it.

3 · Workflow as config

A workflow file is a list of actions — trigger (topic/key/kind/condition, may read board state) → optional body (spawn a node session) → emitter (in-tray, new event, webhook, HITL surface). The 7-stage pipeline becomes ~a dozen actions: signal:finished kind from intake → spawn planning, risk:high event → spawn risk-triage, ask event → HITL emitter. The daemon's tick becomes a generic engine: read new events, match triggers, fire, log.

4 · GitHub adapter

The existing poller shrinks to an adapter: it watches PRs/checks and writes board events (pr-opened, checks-green, merged). Automerge and surface gates become actions like everything else. GitHub stops being half the state store.

What stays untouched

The Rust blackboard crate and its Linear project (the board schema here is a faithful consumer, and swapping SQLite-in-Python for the crate via PyO3 later is mechanical because the vocabulary matches). The blackboard context — referenced only. The stage prompts' content. Surfaces, ask/park/revive, worktrees — they become emitters/actions but keep their behavior. Evals: fixture stories + deterministic claims are the regression net run before and after the refactor.

Proof workflows

Workflow #1: the existing 7-stage pipeline, expressed purely as config, passes a rung-0 fixture story end-to-end with both gates on surfaces — same behavior, zero stage logic in engine code.

Workflow #2 (the agnosticism proof): a genuinely different shape defined in config only. Recommended: a 3-node eval workflow — run-fixture → judge-artifacts → report-to-HITL — because it proves the claim and is the eval runner we want anyway, giving “evaluate individual nodes / e2e workflows” its first real form. Alternative: a trivial 2-node demo (cheaper, proves less).

Risks

Transition messiness — two mechanisms coexisting if we migrate stage-by-stage. Proposal: convert the whole graph in one pass on a branch, with the fixture suite as the gate to swap over.

Semantics drift — a Python semblance that quietly diverges from the decided design would poison the later crate swap. Mitigation: the board module's docstrings cite the decision entries per feature, and anything the decisions don't cover gets flagged to you rather than improvised.

Scope creep — the engine only needs what workflow #1 and #2 use. Kinds or delivery modes nothing exercises yet stay unimplemented (typed but rejected as “not in v0-proto”).
